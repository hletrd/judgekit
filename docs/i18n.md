# Internationalization (i18n)

JudgeKit ships two locales, `en` and `ko`, through [next-intl](https://next-intl.dev)
(`^4.9.1`). Every user-facing string lives in a message bundle; there are no
hardcoded display strings in components.

## Layout

| Path | Purpose |
|------|---------|
| `messages/en.json` | English message bundle |
| `messages/ko.json` | Korean message bundle |
| `src/i18n/request.ts` | Request config — resolves the active locale and loads its bundle |
| `src/lib/i18n/constants.ts` | `SUPPORTED_LOCALES` (`en`, `ko`), `DEFAULT_LOCALE` (`en`), cookie/query-param names |
| `src/lib/i18n/api-error.ts` | `translateApiErrorKey` — safe lookup of an API error code |

Locale resolution order (`src/i18n/request.ts`): `x-locale-override` header →
`locale` cookie → `DEFAULT_LOCALE` when the request is in deterministic
public-locale mode → `Accept-Language` → the `defaultLocale` system setting →
`DEFAULT_LOCALE`.

The two bundles must always hold the **same key set**. Adding a key to one
without the other leaves the other locale rendering a raw key path.

## Adding a string

1. Add the key to **both** `messages/en.json` and `messages/ko.json`, in the same
   position in the same namespace.
2. Read it with a namespaced translator:

   ```tsx
   const t = useTranslations("submissions");          // client
   const t = await getTranslations("submissions");    // server
   t("table.language");
   ```

3. Korean copy follows the house voice already in `ko.json` (`~해요` endings) and
   **must keep the browser/font default letter-spacing** — see the Typography
   rule in `CLAUDE.md`.

`tests/unit/ui-i18n-keys-implementation.test.ts` scans every literal
`t("...")` argument under `src/app` and `src/components` and fails if the key is
missing from either bundle, so a plain literal key cannot regress.

## Keys built at runtime (the trap)

next-intl does **not** return `undefined` for a missing key — it logs an error
and returns the full key path as the string. So a bad key renders as literal
`submissions.status.time_limit_exceeded` in the UI, and a `?? fallback` guard
never fires:

```tsx
// BROKEN — `?? result.status` can never run, and the DB value is not the key
label={t(`status.${result.status}`) ?? result.status}
```

A key assembled from a template literal is invisible to the literal-key test, so
this class of bug ships silently. **Never interpolate an untrusted value into a
message key.** Use one of these instead:

### 1. A lookup map that owns the mapping

Preferred when the runtime value and the message key differ. Submission statuses
are the canonical case: the DB stores `time_limit_exceeded` / `memory_limit_exceeded`
but the bundles key those verdicts as `status.time_limit` / `status.memory_limit`.

```tsx
import { buildStatusLabels } from "@/lib/judge/status-labels";

const statusLabels = buildStatusLabels(t);   // build once, not per row
label={statusLabels[submission.status] ?? submission.status}
```

`src/lib/judge/status-labels.ts` is the single source of truth for that mapping;
`SubmissionStatusBadge` uses the equivalent `statusMessageKey()` switch for its
`statusFull.*` tooltip.

### 2. `t.has()` via `translateApiErrorKey`

For an error code coming back from an API route, where the set of codes is open:

```tsx
import { translateApiErrorKey } from "@/lib/i18n/api-error";

toast.error(translateApiErrorKey(t, getApiError(payload), "assignmentCreateFailed"));
```

It calls `t.has(errorKey)` first and falls back to the supplied key, so an
unknown code degrades to a real sentence rather than a key path.

### 3. An explicit whitelist

For a small closed set, filter through a `Set` (or a `switch`) before the
lookup — `KNOWN_BACKUP_ERRORS` in `database-backup-restore.tsx`,
`KNOWN_SUBMIT_ERRORS` in `problem-set-form.tsx`, `knownErrorKeys` in
`compiler-client.tsx`. **Every member of the whitelist needs a message**; the
whitelist is the contract.

### Server-action error codes

A server action under `src/lib/actions/` returns `{ success: false, error: "<code>" }`
and its caller usually does `toast.error(t(result.error ?? "updateError"))`. That
code **is** a message key in the caller's namespace, so any new code needs a
matching key:

| Action | Consuming namespace |
|--------|---------------------|
| `change-password.ts` | `changePassword` |
| `public-signup.ts` | `auth` |
| `tag-management.ts` | `admin.tags` |
| `update-profile.ts` | `profile` |
| `user-management.ts` | `admin.users` |

Actions whose callers use a fixed message instead (`language-configs.ts`,
`plugins.ts`, `update-preferences.ts`) are exempt — but if you change a caller to
pass the code to `t()`, add the keys first.

### Other runtime-keyed lookups

Values that index a message namespace directly must match the bundle exactly:

- `capabilities.groups.<key>` uses the **`CAPABILITY_GROUPS` object key**
  (`problem_sets`, `anti_cheat`, `recruiting`), not its `labelKey` field.
- `capabilities.items.<capability>` uses the dotted capability id
  (`recruiting.manage_invitations`).
- `nav.<key>` is keyed by `SEGMENT_LABEL_MAP` in `src/components/layout/breadcrumb.tsx`;
  note `publicShell.nav.*` is a **separate** namespace with its own keys.

## Regression tests

`tests/unit/ui-i18n-keys-implementation.test.ts` covers both classes:

| Test | Guards |
|------|--------|
| literal translation keys | every literal `t("...")` under `src/app` / `src/components` |
| submission statuses | every `SubmissionStatus` resolves through `buildStatusLabels` to a real key |
| capabilities | every `CAPABILITY_GROUPS` key and every `ALL_CAPABILITIES` entry |
| server-action error codes | every `error: "..."` in the five actions above |
| known-error whitelists | every member of `KNOWN_BACKUP_ERRORS` / `KNOWN_SUBMIT_ERRORS` / `knownErrorKeys` |
| breadcrumb segments | every `SEGMENT_LABEL_MAP` value under `nav` |

When you add a new runtime-keyed lookup, add it to this file **and** extend that
test — a guard with no test is how the previous batch of keys went missing.

## Known gap

`admin.settings.maxJudgeClaimDurationMs` (and its `...Hint`) have no message.
The key is a `ConfiguredSettings` field that no settings form currently renders,
so nothing breaks today; wiring it into `ConfigSettingsForm` without adding the
two messages first would print the key path.
